# Возврат к DHCP на адаптере без соединения — через MSFT_NetIPInterface

Исключение из [ADR 0002](0002-ipv4-through-netsh.md). Если на адаптере без соединения задать адрес вручную, Windows записывает ручные настройки, но DHCP не выключает до подключения. Что адрес ручной, видно только по флагу `DisableDhcpOnConnect = 1`. Вернуть такой адаптер к DHCP средствами netsh нельзя: `set address source=dhcp` отвечает «DHCP is already enabled on this interface». Поэтому инструмент удаляет ручные адреса и шлюзы командой netsh `delete address … gateway=all`, а затем включает DHCP в постоянных настройках через WMI-класс `MSFT_NetIPInterface` (`root\StandardCimv2`, контекст `PolicyStore = PersistentStore`). То же самое делает `Set-NetIPInterface`, но вызов идёт внутри процесса, без PowerShell. Этот путь — только запасной: он срабатывает, когда после обычных команд netsh адрес всё ещё читается как ручной.

Основание — три прогона разведочных скриптов по #8 на Windows 10 21H2:

- netsh `source=dhcp` отказывает при любой подготовке: удаление адреса, `store=active`, выключение и включение адаптера.
- `delete address` стирает адрес и шлюз, но флаг остаётся. Если оставить так, то при подключении Windows выключает DHCP, и адаптер остаётся без адреса.
- `Win32_NetworkAdapterConfiguration.EnableDHCP` возвращает 84 (IP не включён).
- `MSFT_NetIPInterface` без контекста хранилища ничего не меняет. С контекстом постоянного хранилища снимает флаг, а после подключения адаптер получает адрес по DHCP.

## Considered Options

- **Прямая запись в реестр** (сбросить `DisableDhcpOnConnect`) — отвергнута уже в ADR 0002 как опора на недокументированное поведение.
- **Запуск `Set-NetIPInterface` через PowerShell** — второй дочерний процесс ради одного вызова и лишний повод для антивируса.

## Consequences

- `MSFT_NetIPInterface` появился в Windows 8. Перед удалением адресов инструмент убеждается, что класс доступен. Без класса адреса не стираются: иначе адаптер после подключения остался бы совсем без адреса. Применение при этом сообщает об ошибке. Ведёт ли себя Windows 7 так же, не проверялось.
- Если удалить адрес или шлюз не удалось, DHCP не включается. Иначе оставшийся шлюз скрылся бы от проверки после применения, ведь при автоматическом адресе шлюз не сравнивается.
- Запасной путь работает только на адаптере без соединения. На подключённом адаптере `source=dhcp` срабатывает и так, а сам путь там не проверялся.
- На Windows 11 путь не проверялся.
